# 20

Q: Dans composer.json, quelle différence y a-t-il entre require et autoload ?
+ require liste les paquets à télécharger ; autoload dit où trouver tes propres classes
- require liste tes propres classes ; autoload liste les paquets à télécharger
- require sert uniquement au développement ; autoload sert uniquement à la production
- require et autoload sont deux noms pour la même section du manifeste
? require = dépendances (et version minimale de PHP). autoload = correspondance namespace → dossier pour ton code (PSR-4).

Q: Que fait « composer install » quand un fichier composer.lock existe ?
+ Il installe les versions exactes enregistrées dans composer.lock
- Il recalcule les dernières versions compatibles et réécrit composer.lock
- Il supprime le dossier vendor sans rien réinstaller ensuite
- Il met à jour composer.json avec les nouvelles dépendances disponibles
? composer.lock garantit la reproductibilité : tous les développeurs obtiennent les mêmes versions.

Q: Que fait « composer update » ?
+ Il recalcule les versions autorisées par composer.json et réécrit composer.lock
- Il installe uniquement les versions déjà enregistrées dans composer.lock
- Il met à jour PHP lui-même vers sa dernière version stable
- Il supprime les dépendances que le projet n'utilise plus
? À utiliser volontairement : il peut changer les versions installées.

Q: Quels éléments versionne-t-on dans git pour une application ?
+ composer.json
+ composer.lock
- Le dossier vendor/
- Le fichier vendor/autoload.php
? vendor/ est généré par composer install : on ne le versionne pas (.gitignore) et on ne l'édite jamais à la main.

Q: Avec "psr-4": { "App\\": "src/" }, dans quel fichier se trouve la classe App\Domain\Film ?
+ src/Domain/Film.php
- src/App/Domain/Film.php
- src/domain/film.php
- Domain/Film.php
? Le préfixe App\ est remplacé par src/, les \ deviennent des /, et le nom du fichier est celui de la classe (même casse) suivi de .php.

Q: Pourquoi la casse des noms de fichiers est-elle importante avec PSR-4 ?
+ Sous Linux, Film.php et film.php sont deux fichiers différents
- PHP convertit toujours les noms de classes en minuscules
- Composer refuse tout fichier dont le nom contient une majuscule
- Seul le nom du namespace est sensible à la casse
? Un projet qui marche sous Windows peut échouer sous Linux (serveur, CI) à cause d'une différence de casse.

Q: Où charge-t-on vendor/autoload.php ?
+ Une seule fois, au point d'entrée (par exemple public/index.php)
- Dans chaque classe, au début de son fichier
- Dans chaque fonction qui utilise une classe
- Dans la section scripts de composer.json
? L'autoloader s'enregistre une fois pour tout le processus. Le répéter serait inutile, fragile (chemins relatifs) et mélangerait infrastructure et domaine.

Q: « Class "App\Domain\Film" not found » alors que le fichier existe. Quelle cause est la plus fréquente ?
+ Le namespace déclaré ne correspond pas au chemin du fichier
- Le fichier est trop long pour être chargé par Composer
- La classe est déclarée avec le mot-clé final
- La méthode description() n'est pas déclarée publique
? Namespace mal orthographié, casse du fichier, fichier hors de src/ ou configuration d'autoload modifiée sans dump-autoload.

Q: Quand faut-il relancer « composer dump-autoload » ?
+ Après avoir modifié la section autoload de composer.json
- Après chaque modification du corps d'une méthode
- Avant chaque exécution d'une page web
- Après chaque ajout d'une ligne de HTML
? Il régénère les tables de correspondance (vendor/composer/autoload_psr4.php).

Q: Quelle est la différence entre un script Composer et une dépendance ?
+ Un script est un raccourci de commande ; une dépendance est du code tiers
- Un script est du code tiers ; une dépendance est un raccourci de commande
- Les deux sont du code tiers, installés à des moments différents
- Les deux sont des raccourcis, seul le dossier d'installation change
? "scripts": { "start": "php -S localhost:8000 -t public" } permet de lancer « composer start ».

Q: Que signifie la contrainte de version « ^4.0 » ?
+ Toute version compatible 4.x (au moins 4.0, jamais 5.0)
- Exactement la version 4.0, sans aucune mise à jour possible
- N'importe quelle version à partir de 4.0, y compris 5.x
- Toute version strictement inférieure à 4.0
? ^ suit le versionnement sémantique : pas de rupture de compatibilité à l'intérieur d'une version majeure.

Q: Quelle commande lance le serveur défini par scripts.start dans composer.json ?
= composer start
? Les scripts Composer sont des raccourcis : « composer start » exécute la commande associée (ici php -S …).

Q: Pourquoi ne jamais modifier le contenu de vendor/ ?
+ Il est généré par Composer : tes modifications seraient perdues à la réinstallation
- Les fichiers de vendor/ sont chiffrés
- PHP refuse de charger un fichier modifié de vendor/
- vendor/ est en lecture seule sur tous les systèmes
? Pour changer un comportement, on met à jour la dépendance ou on l'étend, jamais en retouchant son code.

Q: Quelle commande ajoute une bibliothèque au projet et l'inscrit dans composer.json ?
= composer require
? Exemple : composer require firebase/php-jwt. Composer choisit une contrainte (^6.10…), télécharge le paquet dans vendor/ et met à jour composer.lock. Avec --dev, la dépendance ne sert qu'au développement (tests).

Q: Que signifie le sigle PSR ?
+ PHP Standard Recommendation : une recommandation commune publiée par le PHP-FIG
- PHP Secure Request : un format de requête sécurisée
- Package Source Repository : le dépôt central de Composer
- PHP Server Runtime : le moteur qui exécute les scripts
? Exemples : PSR-4 (autoload), PSR-7 (messages HTTP), PSR-15 (middlewares), PSR-3 (journalisation). Les bibliothèques qui les respectent sont interchangeables.

# 21

Q: Que signifie « refactoriser » ?
+ Améliorer la structure interne sans changer le comportement observable
- Ajouter des fonctionnalités en réécrivant tout le code d'un coup
- Corriger uniquement les bugs signalés par les utilisateurs
- Réduire le nombre de lignes quel que soit le résultat
? Un changement à la fois, suivi d'un test (la recette), est plus sûr qu'une réécriture globale.

Q: Pourquoi un fichier qui mélange connexion, SQL, validation, HTML et HTTP est-il un problème ?
+ Il a plusieurs raisons de changer : responsabilités mélangées
- PHP refuse d'exécuter des fichiers de plus de 100 lignes
- Le navigateur ne sait pas interpréter un tel fichier
- Il consomme obligatoirement plus de mémoire que plusieurs fichiers
? C'est le principe de responsabilité unique : un composant, une raison de changer.

Q: Qu'est-ce qu'un « front controller » ?
+ Un point d'entrée unique qui reçoit toutes les requêtes et les répartit
- Un contrôleur chargé uniquement de l'affichage de la page d'accueil
- Un fichier JavaScript qui contrôle les formulaires côté navigateur
- Le premier contrôleur créé dans le projet, par ordre alphabétique
? public/index.php charge la configuration, puis le routeur associe la méthode et le chemin à un contrôleur. Les autres fichiers PHP restent hors du dossier public.

Q: Dans une architecture MVC avec Slim, qui reçoit GET /livres/{id} ?
+ Le routeur, qui fait correspondre méthode et chemin à un traitement
- Le modèle, qui lit l'identifiant dans la base
- La vue, qui choisit le template à afficher
- Le repository, qui connaît l'URL demandée
? Le routeur associe l'URL à un contrôleur ; le contrôleur orchestre ensuite.

Q: Qui vérifie que l'identifiant de la route est valide (entier ≥ 1) ?
+ Le contrôleur
- Le modèle
- La vue
- Le routeur Slim
? Le contrôleur lit la requête, valide les entrées HTTP et choisit la réponse. Le modèle porte les invariants du domaine.

Q: Qui interdit un titre vide (invariant du domaine) ?
+ Le modèle (par exemple dans le constructeur de Livre)
- Le contrôleur, dans chaque action
- La vue, avec l'attribut required
- Le routeur, avant d'appeler le contrôleur
? La règle vaut pour le formulaire, les imports et une future API ; required et NOT NULL la complètent sans la remplacer.

Q: Qui connaît la table livres et écrit le SQL correspondant ?
+ Le repository
- Le contrôleur
- La vue
- Le modèle Livre
? Le repository est l'adaptateur de persistance : SELECT / INSERT avec PDO.

Q: Qui échappe les chaînes avant de les écrire dans le HTML ?
+ La vue, au moment de l'affichage
- Le repository, au moment de la lecture
- Le routeur, avant d'appeler le contrôleur
- Le modèle, dans son constructeur
? htmlspecialchars se fait à la sortie, dans la vue.

Q: Qui choisit entre un 404 et une redirection 303 ?
+ Le contrôleur
- Le repository
- Le modèle
- La base de données
? Le repository retourne null ; le contrôleur traduit en statut HTTP.

Q: Un repository doit-il répondre lui-même par un statut HTTP 404 quand il ne trouve pas la ligne ? [cours]
+ Non : il renvoie null ou une entité ; le contrôleur choisit le statut
- Oui : c'est lui qui connaît la base, donc lui qui sait que la ligne manque
- Oui, mais seulement pour une réponse JSON, jamais pour une page HTML
- Non : il doit lever une PDOException à chaque ligne absente
? Le repository encapsule SQL et PDO ; il ne connaît ni HTTP, ni HTML, ni JSON. Une absence devient null ; le contrôleur la traduit en 404 (page ou objet JSON d'erreur). Une PDOException signale, elle, une panne technique à traiter à part.

Q: Que doit retourner la méthode trouver(int $id) d'un repository quand la ligne n'existe pas ?
+ null : un contrat clair, jamais un false ambigu
- false, comme PDO::fetch
- Une RuntimeException
- Un tableau vide
? La méthode promet « entité ou null » (type de retour ?Livre) : l'appelant sait exactement quoi tester.

Q: Un projet contient des dossiers Model, View et Controller. Son architecture est-elle forcément bonne ? [cours]
+ Non : une architecture se juge aux responsabilités réelles, pas aux noms de dossiers
- Oui : les noms de dossiers garantissent la séparation
- Oui, dès lors que le code fonctionne
- Cela dépend uniquement du CSS
? Si tout le SQL est écrit dans LivreController.php, une responsabilité reste au mauvais endroit.

Q: D'où vient le motif MVC ? [cours]
+ De Xerox PARC et du langage Smalltalk, avec Trygve Reenskaug (1979)
- Du W3C, avec la première version du HTML en 1991
- De Microsoft, avec le framework .NET en 2002
- De Rasmus Lerdorf, avec la première version de PHP
? Le MVC Web est une adaptation du principe original (cycle requête → réponse), pas une copie.

Q: Slim 4 impose-t-il MVC ? [cours]
+ Non : Slim gère HTTP, la séparation MVC est un choix de conception
- Oui : il génère automatiquement modèle, vue et contrôleur
- Oui, mais seulement pour les routes POST
- Non, mais il interdit les repositories
? Slim fournit routeur, PSR-7 et middlewares ; modèle, contrôleurs, vues et repository sont créés par l'équipe.

Q: Qu'est-ce que l'injection de dépendances ? [cours]
+ Fournir à un objet ce dont il a besoin
- Insérer du code SQL dans une requête préparée
- Copier le code d'une classe dans une autre
- Importer des paquets avec Composer
? Dans public/index.php : $repository = new LivreRepository($pdo); $controller = new LivreController($repository, $vue, $csrf);

Q: Pourquoi un repository reçoit-il la connexion PDO par son constructeur ?
+ La connexion est créée une seule fois puis injectée là où elle sert
- Pour que chaque méthode puisse ouvrir sa propre connexion
- Pour rendre la connexion accessible à toutes les vues du projet
- Parce que PDO ne peut être utilisé que dans un constructeur
? La classe reçoit ce dont elle a besoin au lieu de le fabriquer : on peut lui passer une base SQLite en mémoire dans les tests.

Q: Où placer les requêtes SQL d'une application organisée en couches ?
+ Dans le repository ; public/index.php n'en contient aucune
- Directement dans chaque route, près du HTML
- Dans les vues, au plus près de l'affichage
- Dans composer.json, section scripts
? public/index.php peut orchestrer, mais ne contient aucune requête.

Q: Pourquoi le nom du template ne doit-il jamais venir d'un paramètre libre de l'URL ? [cours]
+ Sinon un attaquant pourrait faire inclure un fichier arbitraire du serveur
- Parce que les templates sont chiffrés par la vue
- Parce que l'URL est limitée à vingt caractères
- Parce que PHP interdit les include dynamiques
? PhpView::render fait require __DIR__ . '/../../views/' . $template . '.php' : le nom vient du code, jamais du client.

Q: Le constructeur de Livre lève InvalidArgumentException pour un titre vide. Quel statut renvoie le contrôleur ? [cours]
= 422
? 422 : saisie non conforme aux règles, formulaire réaffiché avec la valeur et le message.

Q: Pourquoi intercepter InvalidArgumentException plutôt que Throwable dans le contrôleur ? [cours]
+ Pour ne pas déguiser des pannes techniques en erreurs métier
- Parce que Throwable n'existe pas en PHP 8
- Parce que Throwable ne peut pas être attrapé
- Pour obtenir un message d'erreur plus court
? Une erreur SQL doit remonter : un middleware la journalise et présente un 500 neutre, jamais un faux 404 ou 422.

Q: Une requête SQL échoue de façon inattendue. Quelle réponse est la plus appropriée ? [cours]
+ Un 500 neutre, avec le détail journalisé côté serveur
- Un 404, pour ne pas inquiéter l'utilisateur
- Un 422 avec le message SQL complet
- Un 200 avec une page blanche
? 404 : absence attendue. 500 : panne, à journaliser. Les traces et chemins internes ne s'affichent jamais en production.

Q: Demain les clients veulent du JSON au lieu de HTML. Que doit-on principalement adapter ? [cours]
+ La représentation de sortie (contrôleur / format), pas le modèle ni le repository
- Le schéma de la base SQLite
- La règle de validation du titre dans Livre
- Toutes les requêtes SQL du repository
? Le même métier peut alimenter plusieurs interfaces : seule la couche HTTP change.

Q: Une interface HTML et une API JSON offrent la même opération. Comment partager les règles métier ?
+ Les deux contrôleurs appellent le même service (ou le même modèle)
- Le contrôleur HTML contient les règles, l'API les recopie
- L'API JSON appelle le contrôleur HTML puis convertit la page
- Les règles sont réécrites dans chaque vue
? Seuls les contrôleurs diffèrent : représentation (HTML ou JSON) et statuts. Une règle écrite une seule fois ne peut pas diverger.

Q: Où placer la règle « le nombre de places ne peut pas être négatif » dans une architecture MVC ? [cours]
+ Dans le modèle ou le service métier, indépendamment de l'interface
- Dans la vue, car c'est elle qui affiche le nombre de places
- Dans le routeur, avant d'appeler le contrôleur concerné
- Dans la feuille CSS, grâce à l'attribut min du champ
? Le modèle porte ses invariants (nom non vide, places ≥ 0). La vue affiche et échappe ; le contrôleur lit la requête et orchestre ; le repository exécute le SQL. Une règle placée dans la vue disparaît dès qu'une autre interface (API mobile) réutilise le domaine.

Q: Quelle règle ne peut pas être garantie par une simple contrainte de colonne ?
+ Un client ne peut pas avoir plus de trois commandes en cours
- Le nom d'un client est obligatoire
- L'adresse email d'un client est unique
- Le montant d'une commande est positif
? La règle porte sur plusieurs lignes : le service la vérifie (dans une transaction) ; NOT NULL, UNIQUE et CHECK couvrent les autres.

Q: Après un refactoring vers MVC, quelles contraintes mesurables peut-on vérifier ?
+ Seule la couche repository exécute du SQL
+ Les vues ne lancent aucune requête
+ Le domaine ne dépend pas du framework
- Les contrôleurs lisent $_POST directement
? Autres contrôles possibles : aucune classe ne lit $_GET ou $_POST, public/index.php reste court, et la recette reste verte après chaque extraction.

Q: Pourquoi initialiser la base (database/init.php) en dehors des routes ? [cours]
+ Afficher une page ne doit pas recréer la structure SQL
- Parce que les routes n'ont pas accès à la base
- Parce que SQLite refuse les CREATE TABLE dans une route
- Parce que le script est plus rapide dans un autre dossier
? L'initialisation se fait une fois, par un script autonome (php database/init.php).

Q: Pourquoi utiliser SQLite pour un projet d'apprentissage ? [cours]
+ Aucun serveur à installer, mais la même API PDO que MySQL
- Parce qu'il est plus sécurisé que MySQL
- Parce qu'il est conçu pour de très gros volumes
- Parce que Slim ne fonctionne qu'avec SQLite
? Limite assumée : SQLite convient à un projet pédagogique ; une application multi-utilisateurs a d'autres contraintes.

Q: Que vérifie un test de vue sur un titre contenant du HTML ? [cours]
+ Que le HTML reçu comme titre est affiché comme texte
- Que la vue exécute le HTML pour mettre le titre en gras
- Que le titre est enregistré en base sans modification
- Que la vue génère automatiquement du JSON
? Exemple : un titre « <b>x</b> » doit apparaître littéralement, pas en gras.

Q: Pourquoi « vérifier que tout fonctionne » n'est-il pas un cas de test ? [cours]
+ Il ne précise ni l'état initial, ni l'action, ni le résultat observable attendu
- Un cas de test doit toujours être automatisé pour compter comme un test
- Un test ne peut vérifier qu'une seule fonction à la fois
- Le mot « fonctionne » est réservé aux tests de performance
? Un test discriminant indique la situation initiale, l'action, le résultat attendu et la propriété vérifiée. Sans cela, on ne peut ni le rejouer ni conclure.

Q: Pour être convaincant à l'oral sur le MVC, quel argument montre une vraie compréhension ? [cours]
+ Je peux tracer une requête, justifier chaque couche et la tester
- J'ai trois dossiers nommés Model, View et Controller
- Mon code est très court
- J'ai utilisé le framework Slim
? « J'ai codé du MVC » ne suffit pas : expliquer le trajet GET /livres/1, les responsabilités et ce qui devient facile à changer.

Q: Que fournit Slim 4 ?
+ Un routeur HTTP, des objets PSR-7 et des middlewares
- Un ORM complet, un moteur de vues et un système d'authentification
- Une interface graphique pour administrer la base de données
- Un langage de gabarits propre à remplacer le HTML
? Slim est un micro-framework : modèle, contrôleurs, vues et repository restent des choix de conception.

Q: Comment lire le segment {id} d'une route /films/{id} dans le callback ?
+ Avec le tableau $args : $args['id']
- Avec $_GET['id'], rempli automatiquement par Slim
- Avec $request->getBody()->id
- Avec la fonction globale getParam('id')
? Les paramètres de chemin sont capturés dans $args et arrivent toujours sous forme de chaînes : à valider.

Q: Comment lit-on la query string ?q=alien dans une route Slim ?
+ $request->getQueryParams()
- $request->getParsedBody()
- $args['q']
- $response->getQuery()
? getQueryParams() pour l'URL, getParsedBody() pour le corps (POST/JSON), $args pour les segments de chemin.

Q: Que faut-il activer pour que getParsedBody() décode un corps JSON ?
+ Le middleware addBodyParsingMiddleware()
- Le middleware addJsonEncoder()
- L'option json.decode dans php.ini
- L'attribut readonly sur la requête
? Sans lui, getParsedBody() ne décode pas le JSON.

Q: Que fait ce code ?
|$response->withHeader('X-Test', '1');
|return $response;
+ Rien d'utile : withHeader renvoie une nouvelle réponse qui n'est pas conservée
- Il ajoute l'en-tête X-Test à $response
- Il lève une exception, car $response est immuable
- Il ajoute l'en-tête puis le supprime au return
? PSR-7 : les objets sont immuables. Il faut écrire return $response->withHeader('X-Test', '1');

Q: Comment produire la réponse d'une route Slim ?
+ Écrire dans $response->getBody() puis retourner la réponse
- Utiliser echo puis appeler exit
- Appeler header() puis http_response_code()
- Retourner directement une chaîne de caractères
? Dans une route Slim, ni echo, ni header(), ni http_response_code() : tout passe par l'objet Response retourné.

Q: Dans quel ordre les middlewares Slim s'exécutent-ils ?
+ Le dernier ajouté est exécuté en premier
- Le premier ajouté est exécuté en premier
- Dans l'ordre alphabétique de leur nom de classe
- En parallèle, sans ordre défini
? Modèle « oignon » : l'ErrorMiddleware, ajouté en dernier, enveloppe tout et attrape les exceptions.

Q: Quand displayErrorDetails peut-il être à true dans addErrorMiddleware ?
+ En local, pendant le développement, jamais en production
- En production, pour aider les utilisateurs à signaler les bugs
- Toujours, car il n'affecte que le journal
- Uniquement pour les requêtes POST
? Les traces PHP et les chemins locaux ne doivent jamais être exposés.

Q: Comment donner un nom à une route et générer son URL ?
+ ->setName('film') puis $routeParser->urlFor('film', ['id' => 7])
- ->name('film') puis url('film', 7)
- ->setUrl('film') puis $router->link('film')
- ->alias('film') puis $app->path('film', ['id' => 7])
? Une route nommée évite d'écrire les URL en dur dans le code.

Q: Comment contraindre le paramètre {id} à des chiffres dans le motif de la route ?
+ /films/{id:[0-9]+}
- /films/{id|int}
- /films/(int)id
- /films/:id[digits]
? Slim utilise des expressions rationnelles après les deux-points. Le paramètre reste une chaîne à valider.

Q: Le callback d'une route Slim doit retourner…
+ Un objet Response (ResponseInterface)
- Une chaîne contenant le HTML
- Un tableau associatif transformé en JSON
- Rien : il écrit directement sur la sortie
? Le résultat d'un contrôleur Slim est toujours une ResponseInterface.

Q: Que signifie PSR-7 ?
+ Les interfaces standard des messages HTTP (requête et réponse)
- La convention de nommage des classes pour l'autoload
- Le style de code recommandé pour les fichiers PHP
- Le standard des conteneurs d'injection de dépendances
? PSR-4 : autoload. PSR-7 : requêtes/réponses HTTP. PSR-15 : middlewares et gestionnaires. PSR = PHP Standard Recommendation.

Q: Dans quel ordre une requête réussie traverse-t-elle les composants ?
+ Client, serveur PHP, middleware, routeur, callback, réponse
- Client, callback, routeur, middleware, serveur PHP, réponse
- Client, routeur, serveur PHP, callback, middleware, réponse
- Client, middleware, callback, serveur PHP, routeur, réponse
? Le statut, les en-têtes et le corps sont décidés dans le callback (ou modifiés par un middleware).

Q: Quelles préoccupations transversales confie-t-on volontiers à un middleware ?
+ Ajouter un identifiant à chaque requête
+ Mesurer la durée de traitement
+ Ajouter des en-têtes de sécurité
- Écrire les requêtes SQL d'un repository
? Un middleware agit avant ou après TOUTES les routes concernées : journal, authentification, en-têtes, gestion d'erreurs. Le SQL reste dans les repositories.

Q: Que signifie une réponse 501 sur une route d'une application en cours d'écriture ?
+ La route existe mais son traitement n'est pas encore programmé
- Le serveur manque de mémoire pour traiter cette route
- La requête du client est mal formée
- L'utilisateur n'est pas autorisé à l'appeler
? 501 Not Implemented : le serveur ne sait pas (encore) exécuter la demande.

Q: Le serveur intégré de PHP (php -S) convient-il à la production ?
+ Non : il sert au développement local
- Oui, il est conçu pour des charges de production
- Oui, à condition d'activer l'option --prod
- Non, sauf avec Slim 4 uniquement
? En production on utilise un serveur web (Apache, Nginx + PHP-FPM) avec HTTPS.

Q: Quelle valeur contient $args['num'] pour la route /films/{id}/avis/{num} et la requête GET /films/7/avis/3 ?
= 3
? Les segments entre accolades sont capturés par nom : id vaut 7, num vaut 3 (toujours des chaînes).

# 22

Q: Quelle méthode HTTP sert à créer une ressource dans une collection ?
= POST
? POST /api/films crée un film : statut 201 et en-tête Location vers la nouvelle ressource.

Q: Quelle est la différence entre PUT et PATCH ?
+ PUT remplace la ressource entière ; PATCH ne modifie que les propriétés fournies
- PUT modifie partiellement ; PATCH remplace la ressource entière
- PUT crée une ressource ; PATCH la supprime
- Ce sont deux synonymes pour toutes les API
? Avec PATCH, le titre n'est pas effacé par omission, une propriété inconnue est signalée, un objet vide est refusé.

Q: Quel statut et quel corps pour un DELETE réussi ?
+ 204 No Content, avec un corps vide
- 200 OK, avec le film supprimé dans le corps
- 201 Created, avec l'URL de la ressource supprimée
- 404 Not Found, avec un message de confirmation
? Ne jamais joindre un corps JSON à une réponse 204.

Q: Que doit contenir la réponse à un POST de création réussi ?
+ Le statut 201, l'en-tête Location et la représentation créée
- Le statut 200 et une page HTML de confirmation
- Le statut 204 et un corps vide
- Le statut 303 et un formulaire pré-rempli
? Location: /api/films/{id} indique l'URL de la ressource créée.

Q: Quelle différence de réponse après la création d'une ressource, côté page HTML et côté API JSON ?
+ HTML : redirection 303 vers la fiche ; JSON : 201 avec Location et la représentation
- HTML : 201 avec Location ; JSON : redirection 303 vers la fiche
- Les deux renvoient 200 avec le même corps
- HTML : 204 sans corps ; JSON : 303 vers la liste
? Une page HTML suit Post/Redirect/Get ; une API renvoie la ressource créée avec son URL.

Q: Un POST /api/messages reçoit un JSON mal formé. Quel statut renvoie-t-on ?
= 400
? 400 : la requête est impossible à lire. Un JSON lisible mais invalide pour le métier donne 422.

Q: Le JSON reçu est lisible, mais la propriété message est vide. Quel statut ?
= 422
? 422 Unprocessable Entity (ou Content) : la demande est compréhensible mais viole les règles métier.

Q: Quel statut annonce une ressource créée ?
= 201
? 201 Created, avec un en-tête Location vers l'URL de la nouvelle ressource.

Q: Rejouer deux fois DELETE /api/films/7 : pourquoi DELETE est-il quand même idempotent ?
+ L'état final du serveur est le même : la ressource est absente
- Parce que la deuxième requête renvoie aussi un 204
- Parce que le serveur refuse la deuxième requête
- Parce que DELETE ne modifie jamais rien
? Idempotent concerne l'effet voulu sur le serveur, pas le statut HTTP à chaque essai (le deuxième appel renvoie 404).

Q: Quelle est la différence entre Accept et Content-Type ? [cours]
+ Accept : format souhaité en réponse ; Content-Type : format du corps envoyé
- Accept : format du corps envoyé ; Content-Type : format souhaité en réponse
- Accept : encodage de la page ; Content-Type : taille du corps
- Ils sont identiques : seul leur nom change selon le navigateur
? Le serveur répond aussi avec un Content-Type (application/json; charset=utf-8).

Q: Quelle différence entre une ressource et sa représentation ? [cours]
+ La ressource est l'entité (le livre n°7) ; la représentation en est un instantané (JSON, HTML)
- La ressource est le JSON ; la représentation est la ligne SQL
- La ressource est l'URL ; la représentation est le statut HTTP
- Les deux termes désignent la même chose
? Changer le titre ne crée pas une nouvelle ressource ; la même ressource peut être servie en HTML ou en JSON.

Q: Un client envoie Content-Type: text/plain à une API qui attend du JSON. Quel statut ? [cours]
= 415
? 415 Unsupported Media Type : le média annoncé n'est pas pris en charge.

Q: Le corps reçu est {"titre":" "} (titre vide après trim). Quel statut ? [cours]
= 422
? JSON lisible mais règle métier violée.

Q: Le corps reçu est { titre: } (JSON invalide). Quel statut ? [cours]
= 400
? Syntaxe inexploitable : l'ordre des contrôles est média (415), syntaxe/structure (400), métier (422).

Q: Que doit retourner GET /api/films quand aucun film ne correspond ? [cours]
+ 200 avec une liste JSON vide : []
- 404 avec un message d'erreur
- 200 avec un objet JSON vide : {}
- 204 sans corps
? Ne jamais remplacer [] par {} selon le nombre de résultats : le type du contrat doit rester stable.

Q: Parmi les six contraintes de REST, laquelle est facultative ? [cours]
+ Le code à la demande
- Le client–serveur
- L'absence d'état de conversation
- L'interface uniforme
? Les contraintes : client–serveur, sans état, cache, interface uniforme, système en couches, code à la demande (optionnel).

Q: Qui a défini le style architectural REST, et quand ? [cours]
+ Roy T. Fielding, dans sa thèse en 2000
- Tim Berners-Lee, lors de la création du Web en 1989
- Leonard Richardson, dans son modèle de maturité en 1999
- Rasmus Lerdorf, avec PHP en 1995
? Richardson propose en revanche une grille de maturité (niveaux 0 à 3), distincte des contraintes de Fielding.

Q: Que signifie « sans état de conversation » (stateless) ? [cours]
+ Chaque requête porte le contexte nécessaire
- Le serveur ne stocke aucune donnée, jamais
- Le client ne doit jamais envoyer de cookie
- Les ressources ne changent jamais d'état
? Les livres persistent dans la base (état de la ressource) ; ce qui est interdit, c'est l'état de conversation côté serveur.

Q: Une session PHP serveur est-elle compatible avec la contrainte stateless stricte ? [cours]
+ Pas strictement : elle introduit un état de conversation côté serveur
- Oui, elle est exigée par REST
- Oui, car le cookie est géré par le navigateur
- Non, mais seulement si elle est HttpOnly
? D'où le choix d'un jeton Authorization pour une API, avec ses propres risques (exposition, durée de vie).

Q: Dans le modèle de Richardson, quel niveau décrit POST /execute avec {"action":"supprimerLivre","id":7} ? [cours]
= 0
? Niveau 0 : une seule porte, HTTP comme transport de procédures (RPC).

Q: Que caractérise le niveau 2 de Richardson ? [cours]
+ Des méthodes et des statuts HTTP utilisés avec leur sens
- Des liens hypermédias qui guident le client
- Une URL unique pour toutes les opérations
- Des ressources identifiées mais manipulées uniquement en POST
? Niveau 1 : ressources identifiées. Niveau 3 : hypermédia (HATEOAS). La plupart des API REST visent le niveau 2.

Q: Que signifie HATEOAS ? [cours]
+ Hypermedia As The Engine Of Application State
- HTTP Authentication Token Encoding And Signature
- Hierarchical API Type Exchange Over A Socket
- Hosted API Testing Environment And Staging
? Un simple champ _links décoratif ne suffit pas : le client doit comprendre les relations exposées.

Q: Renvoyer du JSON suffit-il à rendre une API RESTful ? [cours]
+ Non : il faut aussi les méthodes, les statuts
- Oui : JSON est la définition même de REST
- Oui, tant que l'URL commence par /api
- Non, mais seulement si l'API n'utilise pas SQLite
? JSON est un format, pas une architecture. Une API /execute en JSON ne se revendique pas RESTful sur ce seul motif.

Q: À quoi sert un ETag ? [cours]
+ À valider une représentation pour une requête conditionnelle (If-None-Match, If-Match)
- À chiffrer le corps de la réponse
- À identifier l'utilisateur connecté
- À limiter le nombre de requêtes par minute
? Avec If-Match, on évite la modification perdue (412 Precondition Failed si l'ETag a changé).

Q: Quel est le rôle de CORS ? [cours]
+ Indiquer si une page d'une autre origine peut lire la réponse dans un navigateur
- Authentifier l'utilisateur à la place d'une session
- Protéger contre les requêtes forgées à la place du jeton CSRF
- Chiffrer les échanges entre le client et l'API
? CORS ne remplace ni l'authentification, ni l'autorisation, ni la validation. Ne pas confondre CORS et CSRF.

Q: Renommer le champ JSON « titre » en « nom » dans une API déjà utilisée est… [cours]
+ Un changement cassant pour les clients installés
- Un changement compatible, car la valeur reste la même
- Un changement invisible pour les applications mobiles
- Un simple détail interne de l'implémentation
? Compatibles : ajouter un champ facultatif, documenter un nouveau statut. Cassants : renommer, changer un type, supprimer une route, durcir une règle d'accès.

Q: À quoi sert un fichier OpenAPI (openapi.yaml) ? [cours]
+ À décrire le contrat de l'API : routes, paramètres, exemples, statuts, erreurs
- À configurer automatiquement le serveur web
- À stocker les données de test de l'application
- À remplacer les tests d'intégration
? Utile pour la documentation, la génération de clients et les tests de contrat.

Q: Les routes /api/ doivent-elles démarrer une session PHP ? [cours]
+ Non : la session reste réservée aux formulaires HTML et à leur CSRF
- Oui : elle est nécessaire à chaque requête JSON
- Oui, pour stocker le jeton de la prochaine requête
- Non, sauf pour les requêtes GET
? Une API sans état n'a pas besoin de cookie de session.

Q: Pourquoi GET /api/livres/7/supprimer est-il une mauvaise idée ? [cours]
+ Les robots et préchargeurs suivent les liens GET
- Parce que GET ne peut pas contenir d'identifiant
- Parce que le mot « supprimer » est réservé
- Parce que GET est chiffré et donc plus lent
? GET est sûr : il ne doit pas modifier l'état. Une suppression se fait avec DELETE (ou POST avec CSRF dans un formulaire HTML).

Q: Quelles méthodes sont idempotentes ?
+ GET
+ PUT
+ DELETE
- POST
? POST peut créer une nouvelle ressource à chaque appel. PATCH dépend du sens (« fixer le titre » oui, « ajouter 1 » non).

Q: Une application mobile interroge directement la base SQLite du serveur. Pourquoi est-ce une erreur ? [cours]
+ Les règles métier, l'accès et le contrat doivent passer par l'API
- Parce que SQLite ne fonctionne pas sur mobile
- Parce que SQLite est trop lent pour un mobile
- Parce que le mobile ne sait pas lire de JSON
? Une API n'est pas une base publiée : les clients dialoguent avec un service qui contrôle les demandes.

Q: Une route renvoie toujours 200, même pour un identifiant inconnu. Quel est le défaut ? [cours]
+ Le statut ne reflète pas le résultat
- Aucun : 200 est toujours acceptable en JSON
- Le corps est trop court
- La route aurait dû utiliser POST
? Les codes 400, 404, 422 et 500 ne sont pas interchangeables : le statut et le message doivent coïncider.

Q: Quelles informations ne doivent jamais apparaître dans une réponse d'erreur de l'API ?
+ Les traces d'exception et les chemins locaux du serveur
- Le code d'erreur applicatif
- Le message lisible pour le client
- Les détails de validation champ par champ
? Un message précis est utile ; les traces SQL, les chemins et les secrets internes ne sont jamais exposés.

Q: Quel statut renvoyer pour une pagination incohérente (page=-3) dans GET /api/films ?
= 400
? Refuser avec 400 et un message d'erreur explicite, au format d'erreur uniforme.

Q: Un utilisateur authentifié demande la réservation d'un autre compte. Quand l'API peut-elle répondre 404 plutôt que 403 ? [cours]
+ Quand elle masque volontairement l'existence de la ressource
- Quand le jeton est expiré, puisque l'identité n'est plus connue
- Quand la requête utilise la méthode DELETE, jamais avec GET
- Quand le serveur est trop chargé pour vérifier les droits
? 403 : identité connue mais accès interdit. 404 : choix possible pour ne pas révéler qu'une ressource existe, à condition de l'appliquer partout et de le documenter. 401 concerne une authentification absente ou invalide.

Q: Quelle méthode et quelle réponse pour passer le statut d'une réservation existante à « annulée » ? [cours]
+ PATCH sur la ressource, qui répond 200 avec l'objet modifié
- PUT sur la collection, qui répond 201 avec un en-tête Location
- POST sur la ressource, qui répond 204 sans corps
- DELETE sur la ressource, qui répond 200 avec l'ancien objet
? PATCH modifie partiellement une ressource (ici le seul attribut statut) ; PUT remplacerait la représentation complète. L'état cible est renvoyé dans l'objet mis à jour (200). La cohérence des places disponibles reste à garantir côté implémentation.

Q: Comment une API PHP renvoie-t-elle correctement du JSON, sans framework ?
+ header('Content-Type: application/json; charset=utf-8') puis echo json_encode($donnees)
- echo json_encode($donnees) suffit, le navigateur devine le format
- header('Accept: application/json') puis print_r($donnees)
- echo serialize($donnees) avec le statut 200
? Le Content-Type indique au client comment lire le corps ; on fixe aussi le statut avec http_response_code() quand il n'est pas 200.
